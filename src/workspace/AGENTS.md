# Workspace architecture rules

- Contracts have two routes (accepted proposal, or direct from the lead); `contracts.source` is derived by `ws_contract_guard` from `proposal_id` and never set by the app, so the "no GM quotation" trail can't be forged.
- Brief visibility follows `can_see_lead` only; the unassigned "Submitted" queue (`ws_brief_queue`) is GM-only, so work reaches a designer solely through GM assignment.
- A design version reaches Submitted only via `ws_submit_design_package` (one transaction with the FF&E costing); `ws_design_guard` refuses it unless the lead's costing is exactly Submitted, so renders and costs never go out separately.
- A contract reaches Signed only via `ws_sign_contract(contract, handover)` (one transaction: project, lead → Won, FF&E project_id stamped, four drawing tasks, notifications); `ws_contract_guard` refuses any other path so a signed contract always has a project and a handover date.
- FF&E purchasing band (1 Cabinetry → 5 Kitchenware & linen, labels in PRIORITY_BANDS) is defined only by `ws_ffe_band`, matching item names before category with compounds before bare words; bulk re-bands run under `ws.reband` so they neither mark rows manual nor notify sales (trigger `ffe_items_band`); hand changes set `priority_band_manual` and are never recomputed. A compound item is split into one row per part by `ws_ffe_split_parts` only when its parts fall in different bands, so same-band bundles ("Bed + Mattress") stay one row. Unit cost is editable by the GM and coordinator on the procurement list, and by the GM even while the costing is Submitted.
- Brief FF&E jsonb becomes `ffe_items` only via `ws_seed_ffe_from_brief` (called by `ws_assign_brief`, and from the app only through the permission-checked `ws_seed_ffe`; the browser never inserts seed rows); proposals read `ffe_items` only, with no brief fallback, so a missing list shows up instead of being hidden.
- Drawing tasks mirror uploads: `ws_drawing_changed` on project_files calls `ws_sync_drawing_task` (done iff a file of that kind exists) and `tasks_drawing_guard` refuses hand ticks; kinds and deadlines are defined only by `ws_drawing_kinds`/`ws_drawing_hours` (mirrored by DRAWING_KINDS), tasks are created only via `ws_create_drawing_tasks`, and `tasks.due_at` decides lateness (`due_date` derived from it) so deadlines can be hour-precise.
- A project is created only by `ws_sign_contract` (contract route) or `ws_convert_lead` (fast path, no contract); the fast path accepts an empty FF&E list.
- Deal-record categories are "Signed contract", "Proposal", "Contract" and "Quote" (DEAL_CATEGORIES, mirrored in the project_files policies and can_touch_workspace_object); designers and coordinators can never read or upload any of them. "Signed contract" and "Proposal" project_files are sales/GM-upload deal records, versioned by keeping older files; they may be filed on a lead (lead_id, path deals/<lead_id>/…) and `ws_carry_deal_files` stamps project_id on conversion so one row/object serves both; only these two categories may exist without a project, and drawing triggers act only on the four drawing categories.
- Project stage/risk are writable only by the GM and the project coordinator; overall_pct is derived from stage and proc_pct from ffe_items stages by triggers (no client writes), payments and handover_date only by the GM and sales owner (`ws_project_guard`); the active pipeline is defined only in PROJECT_STAGES, and legacy enum stages are refused on entry.
- Contract value lives only in `project_value_private` (GM + project sales owner); `projects.value` is revoked from staff, so no client query may select it.
- A project with no in-system signed contract (`ws_needs_budget`) buys only after a GM budget approval: `ws_submit_budget` (refuses while any item lacks a supplier or purchase link, per `ws_ffe_gaps`) and `ws_decide_budget` reuse `ffe_costings` states with `purpose = 'budget'` (set only through the `ws.budget` flag), so the coordinator's "procurement" notice comes from approval, never from conversion.
- Leads are deleted only through the `delete-lead` function: it checks `ws_lead_delete_block` (converted → refused for all; signed contract or not owner → GM-only), removes the lead's storage objects (`ws_lead_storage_paths`) first, then deletes the row as the caller so RLS and `leads_delete_guard` apply; a failure before the row delete leaves the lead intact, never stranded files.
- The coordinator sees what to buy and what it costs (ffe_items, ffe_item_costs, suppliers) but nothing the client pays: `ffe_costings.options` has no direct SELECT grant and is read only via `ws_costing_options` (null for coordinators); markup (`ffe_costing_private`), contracts, proposals and project value exclude coordinators.
- Change-request `cost_delta` is client-charged money: no direct SELECT grant, read only via `ws_cr_costs` (empty for coordinators), and `crs_cost_guard` stops coordinators writing it, so they see scope and days only.
- Procurement opens only after the designer (or the GM, always the GM when no designer) confirms the converted FF&E list: `projects.confirmed_at/by`, written only via `ws_confirm_ffe_list`/`ws_return_ffe_list` (GM only)/`ws_submit_budget` under the `ws.confirming` flag; coordinator procurement notices come only from `ws_release_procurement` (confirmed and, where `ws_needs_budget`, budget approved). Edits to a confirmed list keep it confirmed and notify coordinators on the 15-minute debounce.
