# Workspace rules

- Contracts come from an accepted proposal or directly from the lead; `contracts.source` is derived by `ws_contract_guard` from `proposal_id`, never by the app.
- Brief visibility follows `can_see_lead` only; the unassigned "Submitted" queue (`ws_brief_queue`) is GM-only.
- A design version reaches Submitted only via `ws_submit_design_package` (one transaction with the FF&E costing); `ws_design_guard` refuses it unless the lead's costing is exactly Submitted. A Submitted package is re-sent only via `ws_resubmit_design_package` (designer/GM; same completeness bar; notifies GMs and sales), and the designer/GM may edit FF&E while it is Submitted.
- A contract reaches Signed only via `ws_sign_contract(contract, handover)` (one transaction); `ws_contract_guard` refuses others.
- Run 10 "Design (labour)" is NOT a buying run (2026-10-23, Veronica on Luca: wall design "should be under Design, and only labor cost. There's no procurement"). `ws_ffe_kind` gained two rules ahead of cabinetry: `material` (\mmaterials?\M|cladding|fluted|gypsum|plaster|paint|adhesive|mdf|plywood|skirting|cornice) → run 6 with the rest of the building material, and `walldesign` (the word `design`; "designer" is excluded by \M) → run 10. Before this, "Bed Wall Material + fluted panel" and "Dresser wall cladding material" sat in the 24-hour factory order and the four wall designs sat in cabinetry. `ws_order_tasks` names its runs one by one, so run 10 raises no buying task; the app skips it for the amber not-ordered border and leaves it out of "Download orders". `bandOf` returns 0 for an unbanded row ("Unsorted" group) — never the last run, which is now labour.
- FF&E purchasing band (buying-run labels in PRIORITY_BANDS) is defined only by `ws_ffe_band`; item type decides cabinetry/furniture/appliances, the supplier decides online vs pick-up via `ws_ffe_online_supplier` over GM-maintained `ffe_online_retailers` (no client re-band; rows re-derive on next write); names before category, compounds before bare words; bulk re-bands run under `ws.reband` (not marked manual, no sales notice) (trigger `ffe_items_band`); hand changes set `priority_band_manual` and are never recomputed. `ws_ffe_split_parts` splits a compound item per part only when parts differ in band ("Bed + Mattress" stays one row). Unit cost: GM + coordinator on procurement; GM even while Submitted. The categorisation regexes live only in `ws_ffe_kind`, and both `ws_ffe_band` and `ws_ffe_split_parts` read them from there, so a fix goes in one place; `ws_ffe_band` must never gain an overload, because its defaulted `_supplier` makes 3-argument calls ambiguous.
- Brief FF&E jsonb becomes `ffe_items` only via `ws_seed_ffe_from_brief` (called by `ws_assign_brief`, and from the app only through the permission-checked `ws_seed_ffe`; the browser never inserts seed rows); proposals read `ffe_items` only, with no brief fallback.
- Drawing tasks mirror uploads: `ws_sync_drawing_task` (done iff a file of that kind exists AND `in_drive`; un-tick reopens); `tasks_drawing_guard` refuses hand ticks; kinds/hours (24/48/72/72 from `projects.created_at`) only in `ws_drawing_kinds`/`ws_drawing_hours` (mirrored by DRAWING_KINDS; `tasks_drawing_kind_check` uses `ws_drawing_kinds()`); tasks only via `ws_create_drawing_tasks`; `due_at` decides lateness. Designers assigned only by the GM via `ws_assign_lead_designer`/`ws_assign_project_designer`; `ws_project_guard` refuses non-GM changes to designer/coordinator/sales ids.
- A project is created only by `ws_sign_contract` or `ws_convert_lead` (no contract; FF&E may be empty).
- Deal categories: "Signed contract", "Proposal", "Contract" and "Quote" (DEAL_CATEGORIES, mirrored in project_files policies, can_touch_workspace_object); designers/coordinators never touch them. "Signed contract" and "Proposal" project_files are sales/GM deal records; may sit on a lead (deals/<lead_id>/…) and `ws_carry_deal_files` stamps project_id on conversion; only these two may lack a project; drawing triggers skip them.
- Project stage/risk: GM and project coordinator only; overall_pct is derived from stage and proc_pct from ffe_items stages by triggers (no client writes), payments and handover_date only by the GM and sales owner (`ws_project_guard`); the active pipeline is defined only in PROJECT_STAGES, and legacy enum stages are refused on entry.
- Contract value lives only in `project_value_private` (GM + sales owner); `projects.value` is revoked from staff.
- A project with no in-system signed contract (`ws_needs_budget`) buys only after GM budget approval: `ws_submit_budget` (refuses while any item lacks a supplier, per `ws_ffe_gaps`) and `ws_decide_budget` reuse `ffe_costings` states with `purpose = 'budget'` (set only through the `ws.budget` flag).
- Leads are deleted only through the `delete-lead` function: it checks `ws_lead_delete_block` (converted → refused for all; signed contract or not owner → GM-only), removes storage (`ws_lead_storage_paths`) first, then deletes the row as the caller (RLS + `leads_delete_guard`).
- `leads.budget` is the client's money too, and it was showing on every brief card and in the briefs table — the designer's complaint on 2026-10-19 ("why can I still see the contract value on briefs?"). The table-wide SELECT/INSERT/UPDATE grants on `leads` were replaced with per-column grants for every column EXCEPT `budget` (the shape `projects` already had), so no client role can read or write it through PostgREST. `ws_lead_budgets()` returns it to the GM and the lead's sales owner, `ws_set_lead_budget(lead, amount)` writes it, and `useLeadBudgets`/`useSetLeadBudget` are the only app paths — `Lead` is `Omit<Row, "budget">` so the compiler catches any new leak. A designer's map is empty, so the budget line simply disappears from their briefs. Watch out: a column-level REVOKE does nothing while a table-wide grant stands.
- The Stage 1 sales playbook (first client call) is `pages/SalesPlaybook.tsx`, which `pages/Guide.tsx` renders for sales and the GM; the page is on their nav (`PAGES_BY_ROLE`, labelled "Playbook"), and the coordinator keeps their own notes on the same route. It came from the GM's `Aziza_Home_Stage_1_Sales_Playbook.pdf` and then her `Aziza Sales Call Guide.html` (both 2026-10-19, the HTML superseding the PDF: it adds the turnkey golden rule, the package-vs-custom pricing rule, the short answers and the tick list). Both were written into the app rather than attached, so there is one copy, it is searchable and it reads on a phone mid-call; the PDF is deliberately NOT in `public/` because that folder is world-readable and the "never promise" list is internal. Client-facing wording inside `<Script>` is the GM's own and is changed only when she changes it. The new-lead form links to it, since those fields are the call sheet. The Stage 1 tick list is per browser (`ws.playbook.stage1`) with a "Start a new call" reset — it is a call aid, not a record. The page prints: "Print / Save as PDF" opens every disclosure (`usePrintableDisclosures`), hides the nav and the buttons (`playbook-hide-print`) and sets A4 — so the PDF handout is produced FROM this page and cannot drift from it again. The 20 Oct 2026 PDF (`Aziza_Stage1_Sales_Playbook_2026-10-20.pdf`) was rendered from the same copy; if a newer one is ever needed, print the page rather than editing a document.
- Only sales and the GM ever see what the client pays. `ffe_costings.options` has no direct SELECT grant and is read only via `ws_costing_options`, which returns null for coordinators AND designers; `ffe_costing_private` (markup, GM notes, return note) is GM-read-only — cost x markup is the client price, so a designer reading both would be reading the contract value. The designer and coordinator get the notes alone through `ws_costing_notes` (null for sales), which is how "Returned by GM: …" still reaches the designer. Contracts, proposals and `project_value_private` exclude both of them. What the designer and coordinator do see is cost: `ffe_items`, `ffe_item_costs`, suppliers. Veronica, 2026-10-19: "from the designer interface, they shouldn't be able to see the contract value. They can only put the cost of the items."
- Change-request `cost_delta` is client-charged money: no direct SELECT grant, read only via `ws_cr_costs` (empty for coordinators), and `crs_cost_guard` stops coordinators writing it.
- Procurement opens only after the designer (or GM) confirms the converted FF&E list: `projects.confirmed_at/by`, written only via `ws_confirm_ffe_list`/`ws_return_ffe_list` (GM/coordinator)/`ws_submit_budget` under `ws.confirming`; coordinator procurement notices come only from `ws_release_procurement` (confirmed and, where `ws_needs_budget`, budget approved). Confirmed-list edits stay confirmed; coordinators notified on the 15-min debounce.
- An unbuyable item returns to the designer only via `ws_ffe_out_of_stock` → `ws_ffe_reselected` → (`ws_ffe_decide_change` if it costs more), or comes straight back when the supplier restocks via `ws_ffe_back_in_stock` (coordinator/GM; refused once the designer has changed the product; restores the stage saved in `review_prev.stage`, else Awaiting Quote; closes re-choose tasks with no item still out of stock); `ffe_items.review*` has no UPDATE grant and `ws_ffe_review_guard` refuses direct writes and ordering stages on held items; confirmed-list changes reach the GM; a raised line total holds the item.
- `ffe_items.internal` is derived from the section name by `ws_ffe_internal_section`/`ffe_items_internal` (no INSERT/UPDATE grant); such rows are excluded from proposal and contract at `useProposalItems` (sole source for both); hidden from sales in the UI; belong to a project.
- Proposal pages group design images by room (renders, then mood-board kind); only room "Mood Board" images feed the trailing mood-board page; a mood-board kind never changes an image's room.
- Workspace orientation content is role-keyed in `GUIDES`; only roles with guide content and explicit `PAGES_BY_ROLE` access receive navigation, so future role guides remain isolated.
- Coordinator deadline tasks are database-scheduled rows carrying `auto_kind`, `due_at` and instruction `detail`; the project Tasks tab displays Ordering and On site groups by deadline in Dubai time, with no money. `contractor_in` updates refresh project/tasks after triggers re-date the switch run; the partial unique index `tasks_auto_once` makes tasks idempotent, and `ws_sync_drawing_task` only ticks tasks with `auto_kind IS NULL` so an upload never closes the coordinator's order task.
- Signing a contract re-takes `doc.sections` from the live client-facing FF&E list via `ws_sync_contract_items` (called inside `ws_sign_contract`); it refuses on an empty list rather than wiping the document, and keeps the issued list in `doc.sectionsAtIssue`.
- The coordinator sees design images for their own projects via `ws_coordinator_on_lead` — a SELECT policy on `designs`/`design_images` and the `designs/` branch of `can_touch_workspace_object`; `can_see_lead` itself is deliberately unchanged so proposals, contracts and deal records stay closed to them.
- `projects.on_site_by` overrides the three-day on-site rule per project; `ws_handover_tasks` reads it and the `projects_handover_tasks` trigger watches both date columns, so changing either reschedules the run.
- Building/site material belongs to the Dragon Mart pick-up band in `ws_ffe_band` via `ws_ffe_internal_section` before any kind test; the site run is wallwork → delivered → handyman + wallpaper → operations + qc, spaced a day apart from the on-site date and capped at handover − 1.
- `ffe_items.ordered_on` is stamped with today's Dubai date by `ws_ffe_ordered_on_trg` (trigger `ffe_items_ordered_on`) whenever an item moves out of the pre-order stages into Ordered or later (not "Issue / Replacement") without a date; a date already entered is never overwritten. "Order all from supplier" sends one chosen order date (default today) to every item that lacks one.
- An FF&E edit is ONE round trip: `useUpdateFfeItems` writes the row and the cost in parallel, the UPDATE returns the row (`.select(FFE_BASE)`) as the BEFORE triggers left it — band re-derived, `ordered_on` stamped — and `patchFfeRows` puts that into every `["ws","ffe"]` cache. Only the supplier badge (supplier/stage/review changes) and, on a stage move, the project queries are invalidated; an error falls back to `invalidateFfe`. It used to be four round trips per cell (write, rows, costs, badge), which on Veronica's connection on 2026-10-23 (~1s per request to ANY host — the database itself answers in 16ms) made editing feel broken. `useFfeItems` also keeps a 10s `staleTime` so switching Table / Delivery / phase board does not refetch 80 rows. Never go back to blanket invalidation on a cell edit.
- In Procurement, any edit on a row that is part of a multi-row selection (stage, PO ref, notes, buying run, unit cost, dates) applies to every selected row (`applyRow`); clearing stays per row; stage and unit cost skip held rows. Procurement dates are set in bulk two ways: the selection bar's "Apply date" (ETA / Delivered / Ordered / Installed), and picking a date on any row that is part of a multi-row selection, which writes it to every selected row. Clearing a date stays per row. Bulk dates also reach held items — a date is a fact, not a buying decision.
- Procurement has two downloads, neither carrying money. "Download list" is the final-inspection checklist in the on-screen grouping. "Download orders" (`downloadOrdersCsv`) is the receiving checklist Janeshvel asked for on 2026-10-19 ("easier for him to check if this order has been reached, by supplier and different order number"): a summary of every supplier+order with items, pieces, order date, latest ETA, delivered count and state (Complete / Part delivered / Waiting / Not ordered yet), then each order's items under its own heading. The same grouping is on screen as Group by → Order (`byOrder`, supplier then `po_ref`, unnumbered items last in their shop), where an order group offers "Whole order arrived today". "Order all from <shop>" pre-fills the order number with `nextOrderNo` ("Order 1", "Order 2", … per shop), still editable to the shop's own invoice number.
- The Procurement "Driver list" (`DriverList.tsx`) is the only text that leaves the company for a pick-up: buying run 6 (Dragon Mart) items, grouped by shop, merged by item + size, with the supplier book's number (the item's own contact only when the book has none). It must never carry prices, rooms or client names. Delivered/closed and held items are left out; not-ordered items are marked "call first".
- `projects.delivery_address` (free text: building, flat, floor, map link, site contact) is where pick-ups go; any assigned staff member or the GM can set it, from the Driver list dialog. Without it the driver list falls back to property/unit/location and tells the driver to confirm the flat number.
- When a contract becomes Signed, `contracts_delivery_address` (`ws_contract_address_trg` → `ws_contract_delivery_address`) fills an empty `projects.delivery_address` with "<unit no.> <building>, <location>" from the contract — only when the contract's Unit no. is filled. A hand-entered address is never overwritten.
- The agreement's content lives once, in `contractBlocks`; `useContractPages` packs them onto fixed 794×1123 pages, used both for the agreement's own PDF (`AgreementPages`, also its on-screen preview) and the combined "Proposal + agreement" document (`CombinedView`). Don't go back to a flowing print with repeating thead/position:fixed head and foot — Safari doesn't repeat them per page, so they ran over the text, so the whole job prints under the proposal's single margin-0 @page in every browser. Clauses never split; the goods table splits by row with its header repeated, never leaving a room heading last on a page.
- The combined "Proposal + agreement" takes either the workspace's own proposal or a PDF/image filed under the lead's "Proposal" deal record (`SALES_PROPOSAL`); it can be uploaded from inside the combined view. An uploaded PDF is drawn page by page by pdf.js (`uploadedPages.tsx`, lazy chunk, pdfjs-dist 3.11 for older Safari, `isEvalSupported: false`) into 794×1123 image pages, so it prints in the same run as the agreement.
- In the combined document the agreement always comes first; the proposal follows as its appendix behind an "Appendix · Proposal" divider (`AppendixPage`). When the proposal has more than one price (workspace options, or Option A/B columns read from an uploaded PDF), Save as PDF stays locked until sales choose the one stated in the final document; only that option is kept on the proposal pages.
- Client feedback after a design is accepted (usually on a sent proposal) goes to the designer only via `ws_request_redesign(lead, feedback, proposal)` (sales owner/GM): it opens the next design version as a Draft carrying the previous images and `designs.revision_request`, or appends to a Draft already open; refuses while the latest version is Submitted (use Request changes); moves the brief Design Approved → In Design (or Design Ready → Revision Requested) per `ws_brief_guard`; notifies the designer and GMs and gives the designer a "Redesign … — client feedback" task, which `ws_submit_design_package` closes. The resubmitted package sends the FF&E back to the GM for a new quote; the proposal then picks up the new design and price on "Save as new revision".
- `WorkspaceProvider` reloads the workspace (`loading`, which blanks everything behind `Gate`) only when the signed-in person changes; Supabase's auth events on tab refocus/token refresh for the same user must never set `loading`, or every open dialog and half-filled form is lost. Shared `DialogContent`/`SheetContent` ignore outside clicks and focus (close on ✕, Cancel or Esc only). The new-lead form keeps a sessionStorage draft until saved or closed, and the Leads page reopens it after a tab reload.
- Package proposal covers use the photo of the tier being sold (`buildPackageDocument`), not the style `hero`: the cover is full-bleed portrait, so a 675x429 landscape hero keeps only its middle 45% — on Japandi the pendant and the curtains, which is what Veronica saw on 2026-10-26. The cover fade now starts at 56% (was 30%) so the photograph fills the page. Catalog photos are small (hero 675x429, essential 584x793, premium/luxury 528x513) and get upscaled onto a 794x1123 cover: replacing them with files at least 1600px tall is the only way to make the cover crisp.
- The item list shares its last page with the price whenever it can: `combinedPageCap` is 104 and `combinedDensePageCap` 116 (per extra option, minus 8). Both were MEASURED in headless Chrome against the real 710px column, not guessed — 104 fits with room, 108 overflows at normal size, and the `.ppd-dense` setting (10.5px rows, tighter leading) holds ~116. A list over the normal cap renders the combined page dense rather than splitting into "Item list 1 of 2". An 84-item 1-bedroom list is weight 96.2, which under the old cap of 96 missed by a fifth of a row.
- Proposals have two sources. "design" (default): designer renders + the GM's quotation. "package" (`line_items.source = 'package'`, built by `buildPackageDocument` from `packageCatalog.ts`): sales picks a catalog style (photos in `public/catalog/<slug>/`, served as site files — `isCatalogPath`, never signed), the tiers to offer and the standard item list; prices are the price list (`package_prices`, mirrored in `PACKAGE_PRICES`), by the lead's unit type (`ws_package_layout`). `ws_proposal_price_guard` refuses a package price below `ws_package_floor` (list price less the largest GM-approved discount for that tier label) and any non-tier label; `ws_request_discount` prices package requests from the list. A package proposal never pulls designer renders or a GM quote, and has no FF&E sync or redesign.
- A package price request carries the proposal's item list to the GM: `ws_request_discount` calls `ws_package_snapshot`, which stores `[{room,item,qty,unit_cost}]` in `package_costings` (GM-only SELECT; unit costs pre-filled from `ws_ffe_price`, GM-entered costs kept across re-requests; writes only via `ws_package_save_costs`, GM). `PackageCostCheck` shows the GM total cost and margins (20% floor in red) and sends one final price as an approved discount; sales see only that price ("Use this price").
- A lead with no FF&E list gets its project list from its package proposal: `ws_seed_ffe_from_package(lead, project)` (accepted package proposal, else the latest) inserts its item list as `ffe_items` with unit costs from the GM's `package_costings`, else the price book. `ws_sign_contract` calls it before refusing an empty list, and `ws_convert_lead` before `ws_seed_ffe_from_brief`; a designer's list always wins (no-op when items exist). With no designer, `ws_request_ffe_confirm` asks the GM to confirm.
- Package proposals carry `pkg.units` (identical apartments priced together): each option is the unit list price × units, the item list stays per apartment, and the investment heading says "· N units". The DB reads units with `ws_package_units`; `ws_package_floor(lead, label, units)` and package `ws_request_discount` multiply the list price by it, and the GM cost check multiplies the per-unit cost by it.
- Package cost lists (`package_costings`) carry the prices sales asked for, so SELECT is the GM's alone (2026-10-19); writes still go through `ws_package_save_costs` (`ws_can_cost_package`). A designer costs package items on the FF&E list itself, which is where `PackageCostCheck` reads them from anyway once the lead has one. Trigger `proposals_package_costing` keeps each package proposal's list in step with its item list and prices (costs entered are kept) and, on a new package proposal for a lead without a designer, asks the GMs to assign one. `PackageCostCheck` shows on the proposal, GM only.
- A package lead is set up like any other (`ws_package_lead_setup`, run by the package-proposal trigger): its FF&E list is seeded from the package proposal (`ffe_items` + costs, the single source from then on) and it gets a brief marked `extra.package` — Submitted (GM assigns from the queue) or, with a designer, Design Approved (`ws_assign_lead_designer` approves it under `ws.package_brief`, the only bypass in `ws_brief_guard`). `DesignPackage` shows such a lead as its FF&E list only (no renders) while it has no design; the GM's price check reads costs from that FF&E list. A lead with a designer's design never gets this.
